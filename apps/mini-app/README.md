# Telegram Mini App

Приложение для «Ярмарки украденной магии»: сервер хранит состояние игры и проверяет каждое действие, клиент показывает игрокам и ведущему их экраны внутри Telegram.

## Сюжетная редакция на 17 игроков

Новые пустые партии используют `hidden17.narrative` версии 2. Таверна — главный экран, цели и знания личные, сведения об обряде приходят из документов. Источник текстов — `docs/design/gm-book/narrative-17.json`. Книга и личные HTML-вводные строятся из того же файла.

Сохранённая партия не меняет правила при перезапуске сервера. Ведущий переводит её кнопкой **«Включить сюжетную редакцию»** на вкладке «Состав». Переход сохраняет имущество и привязки, возвращает резервы незавершённых прежних предложений, заказов и приглашений в кости. Начатые броски сначала нужно закончить. После начала финала переход недоступен. Уже открытой старой партии сохраняется ранее показанное знание обряда; новые партии начинают с тайными источниками. Сброс реальной игры для обновления не требуется.

Сделка состоит из предложения, ответа получателя и окончательного подтверждения автора. Оба набора зарезервированы, пустой ответ означает подарок. Материалы покупаются за 2 и продаются мастеру за 1 золотой. Публикация объявления не резервирует награду; доска и кубики также используются физически.

В «Итогах» ведущий оценивает два стремления героя: достигнуто, частично, не достигнуто; добавляет пояснение. Неоценённая цель остаётся неоценённой. До раскрытия эпилога оценки скрыты от игроков.

Проверка новой редакции: `pnpm exec playwright test -c e2e/narrative.config.ts`. Для воспроизведения старого hidden17 в тестах предусмотрено `FAIR_NARRATIVE=legacy`; прежний режим 30 ролей — `FAIR_RULESET=legacy`.

## Что здесь лежит

Четыре пакета в одном pnpm-воркспейсе:

- `packages/shared` (`@fair/shared`) — правила игры без ввода-вывода: типы, команды и события, чистые функции `decide` (проверяет команду и возвращает события), `reduce` (применяет событие к состоянию) и `execute` (обе сразу), проекции состояния для игрока и ведущего.
- `packages/server` (`@fair/server`) — Fastify, WebSocket, SQLite, вход через Telegram, бот.
- `packages/client` (`@fair/client`) — Vite и Preact, экраны игрока и ведущего.
- `packages/sim` (`@fair/sim`) — симулятор вечера: боты проходят три акта против настоящего сервера и проверяют результат ([README](packages/sim/README.md)).

Сквозной тест лежит в `e2e/`.

## Установка

Нужны Node 20 и pnpm 9.

```sh
pnpm install
```

## Запуск в разработке без Telegram

Вход через Telegram в разработке заменяет «ручной» вход по коду. В первом терминале запустите сервер:

```sh
cd packages/server
DB_PATH=./data/dev.sqlite ALLOW_DEV_AUTH=1 SESSION_SECRET=dev pnpm exec tsx src/index.ts
```

Во втором терминале запустите клиент:

```sh
pnpm --filter @fair/client dev
```

Vite проксирует `/api` и `/ws` на `localhost:8080`. Если сервер слушает другой порт, задайте его переменной `API_PORT` при запуске клиента, например `API_PORT=8091 pnpm --filter @fair/client dev`. Это переменная Vite, а не сервера, поэтому в `.env.example` её нет.

Код ведущего сервер печатает в лог при старте строкой «Код ведущего». Коды ведущего и всех ролей также отдаёт `GET http://localhost:8080/api/dev/codes` (только при `ALLOW_DEV_AUTH=1`).

Ссылка для входа выглядит так:

```
http://localhost:5173/?dev=<число>&code=<код>
```

`<число>` — любой выдуманный идентификатор пользователя (у каждого открытого окна свой), `<код>` — код ведущего или роли. Окна разных людей открывайте в разных профилях браузера или в приватных окнах. `ALLOW_DEV_AUTH=1` нельзя включать на настоящей игре.

## Переменные окружения

Скопируйте `.env.example` в `.env` и заполните:

| Переменная | Назначение |
| --- | --- |
| `BOT_TOKEN` | токен бота от BotFather; без него сервер не стартует, если не включён `ALLOW_DEV_AUTH=1` |
| `BOT_NAME` | имя бота без `@`, из него строятся ссылки-приглашения |
| `SESSION_SECRET` | секрет подписи сессий, случайная длинная строка |
| `CLIENT_URL` | адрес клиента, который открывает бот |
| `DB_PATH` | файл SQLite (`:memory:` для тестов) |
| `CONTENT_PATH` | файл с данными игры; по умолчанию `docs/design/game-data-v0.2.json` |
| `CONTENT_PATCH_PATH` | файл поправок к ролям на конкретный вечер (см. «Поправки содержимого»); пусто = без поправок |
| `PORT` | порт сервера, по умолчанию 8080 |
| `ALLOW_DEV_AUTH` | `1` включает вход по коду без Telegram, только для разработки; с ним `GET /api/health` отдаёт ещё и память сервера (`memory: { rss, heapUsed }`) |
| `BOT_POLLING` | `1` запускает бота в режиме опроса |

Токены и секреты в Git не кладите.

## Поправки содержимого

Имена и тексты ролей на конкретный вечер (например, Мира становится Мироном, когда роль достаётся мужчине) не правят в `docs/design/game-data-v0.2.json`, а описывают в файле поправок в `apps/mini-app/content/` и указывают его в `CONTENT_PATCH_PATH`. Формат: объект `roles`, где ключ это ключ роли (`o3`), а значение это поля роли, которые нужно заменить; `acting` сливается по полям, остальные поля, включая `contacts`, заменяются целиком. Поле `female: true` отмечает женскую роль с именем не на -а/-я (Сив): без него клиент судит о роде по окончанию имени. Неизвестный ключ роли это ошибка запуска. Пример: `content/2026-10-31.json`. В образе Docker папка `content` лежит в `/repo/apps/mini-app/content`.

## Проверки

```sh
pnpm test        # модульные тесты всех пакетов
pnpm typecheck   # проверка типов
pnpm e2e         # сквозной тест в браузере
pnpm sim -- --players 30 --seed 7   # прогон вечера на 30 ботов, отчёт в packages/sim/sim-out
pnpm sim:load -- --players 30 --minutes 10 --seed 1    # нагрузка: 30 ботов 10 минут
pnpm sim:load -- --players 30 --minutes 120 --seed 1   # нагрузка на всю длину вечера
pnpm sim:bench   # время сборки проекций на 30 игроков при 0, 2000 и 8000 предложений, без сервера
```

`pnpm test` включает тест вечера: 12 ботов проходят вечер от состава до показа итогов против сервера, поднятого в процессе. Прогон на 30 в `pnpm test` не входит, его запускают `pnpm sim`. `pnpm sim:load` держит ярмарку в акте I, каждый бот делает ход примерно раз в 10 секунд, а прогон меряет задержки, размеры проекций и память сервера; отчёт `packages/sim/sim-out/load-<игроков>-<минут>.md`, при нарушении критериев код выхода 1. Двухчасовой прогон стоит повторить перед праздником. Параметры и проверки описаны в [README симулятора](packages/sim/README.md).

Для `pnpm e2e` Playwright сам поднимает сервер (порт 8091, база в памяти) и клиент (порт 5191). Если браузера нет, один раз выполните `pnpm exec playwright install chromium`. Тест проходит весь путь: ведущий собирает состав на 12 и открывает ярмарку, Грета покупает пыль, создаёт Фокус силы и продаёт его Серафине, Серафина принимает сделку.

## Что входит в эту версию

Вход, соединение с сервером в реальном времени, экраны игрока (роль, сумка, сделки, мастерская, алтари, события, итоги) и ведущего (состав, пульт, итоги), серверная проверка команд, способности, лоты, закрытие ярмарки и выгрузка журнала. Подготовка к живому вечеру (этап 7, [спецификация](../../docs/superpowers/specs/2026-10-27-live-night-design.md)):
- ведущий отмечает опоздавших и ушедших и после открытия;
- код ведущего пересдаётся с сервера (`DEPLOY.md`, «Пересдача кода ведущего»);
- на паузе сделки стоят;
- содержимое игры приходит ведущему один раз при подключении;
- проекции не растут со временем: ведущий получает ожидающие сделки и последние 100 обменов, игрок свои ожидающие сделки и 20 последних закрытых;
- клиент сам переподключается и предлагает «Повторить» при неудачном входе.

Порядок вечера для ведущего описан в [памятке](../../docs/design/gm-runbook.md). Что вошло в первую версию и что отложено, описано в разделах 2 и 14 [спецификации](../../docs/design/mini-app-spec.md); порядок работ — в [плане](../../docs/superpowers/plans/2026-10-23-mini-app-core.md). Всё, что там отнесено к следующим этапам, здесь не реализовано.

## Развёртывание

Клиент и сервер должны быть на одном origin: клиент обращается к `/api/...` и `/ws` относительно своего адреса. Сборка и запуск:

```sh
pnpm install
pnpm --filter @fair/client build   # статика в packages/client/dist
cp .env.example .env               # заполнить BOT_TOKEN, BOT_NAME, SESSION_SECRET, CLIENT_URL
pnpm start                         # сервер на PORT (по умолчанию 8080)
```

`pnpm start` запускает `packages/server` через `tsx`, поэтому относительный `DB_PATH` (по умолчанию `./data/session.sqlite`) считается от `packages/server`. Лучше задать абсолютный путь.

Пример `Caddyfile` (домен и путь к репозиторию замените своими):

```
fair.example.org {
	handle /api/* {
		reverse_proxy localhost:8080
	}
	handle /ws {
		reverse_proxy localhost:8080
	}
	handle {
		root * /srv/halloween-2026/apps/mini-app/packages/client/dist
		try_files {path} /index.html
		file_server
	}
}
```

Caddy сам получит сертификат и проксирует WebSocket без отдельных настроек. `try_files` отдаёт `index.html` на любой путь клиента.

- Нужен HTTPS: Telegram открывает Mini App только по `https`. Проще всего поставить перед сервером Caddy, он сам получит сертификат.
- В BotFather создайте бота и задайте Main Mini App URL (адрес клиента, то есть `CLIENT_URL`). Ссылки-приглашения имеют вид `https://t.me/<бот>?startapp=<код>`.
- `BOT_POLLING=1` включает опрос Telegram без вебхука; для одного процесса этого достаточно.
- `ALLOW_DEV_AUTH` на проде держите равным `0`.

## Выгрузка журнала

Кнопка «Скачать журнал» на пульте открывает `/api/gm/export` с токеном ведущего. Ответ: журнал событий и состояние без Telegram id, привязок, кода ведущего и кодов приглашений, имя файла `evening-<дата по Москве>.json`. Тот же файл сервер сам пишет в `<папка DB_PATH>/exports/evening-<closedAt>.json` при закрытии ярмарки и перезаписывает при показе итогов и после каждого исправления. При `DB_PATH=:memory:` файл не пишется.

## Сброс

Перед новой игрой ведущий нажимает на пульте «Сбросить игру». Явка, привязки игроков и игровой прогресс сбрасываются, коды приглашений выдаются заново, ведущий остаётся привязанным. При обычной настройке сервера новая партия сразу получает сценарий на 17 героев. Ссылки, разосланные до сброса, перестают работать.

## Чего пока нет

- Двухчасовой прогон после этапа 8 показал, что рост задержки из-за закрытых сделок устранён: p50 со второй минуты держится в пределах 18–24 мс против 442 мс к 120-й минуте до правки. В первом прогоне после правки была одна минута с p95 702,7 мс, причина не установлена; повторный прогон прошёл все критерии с p95 не выше 49,6 мс за любую минуту ([итоги](../../docs/superpowers/specs/2026-10-28-compact-offers-design.md), раздел 7).
- Движок хранит в состоянии ожидающие предложения и по 20 самых новых закрытых на каждого участника, полный список лежит в журнале событий. Обмены и записи действий не уплотняются, 8000 обменов добавляют около 1 мс на сборку проекций.
- На вкладке «Сделки» игрок видит только 20 последних закрытых сделок; более старые пропадают из списка.
- Структурные контакты и второй ведущий ([спецификация приложения](../../docs/design/mini-app-spec.md), §15–16), передача роли ведущего из интерфейса.

## Новые правила: 17 игроков

Новый пустой журнал открывается в режиме `hidden17`: состав фиксирован, ведущий отдельно. Полный сценарий загружается только сервером из `docs/design/gm-book/hidden-17.json` (`HIDDEN_SCENARIO_PATH` переопределяет путь). `FAIR_RULESET=legacy` оставлен для старого симулятора/регрессионных прогонов; он влияет только на создание пустой партии.

Существующий журнал воспроизводится по прежним правилам, без сброса вещей и ссылок. Для новой игры осознанно сбросьте старую на пульте: при обычной настройке сервера сценарий для 17 игроков включится автоматически. Дополнительное переключение в составе не требуется. Обновление сервера само по себе не меняет текущую партию. При `FAIR_RULESET=legacy` сброс старой партии сохраняет прежние правила; в подготовке остаётся ручной переход «Сценарий для 17 игроков».

- **Роль:** только личная цель, предыстория, известные способы, первые контакты и общие правила. Чужие цели и полная книга не отправляются игроку.
- **Мастерская:** заказ мастеру доступен всем. Собственное ремесло — у Греты, Клёпы, Ады и Вельды в пределах своих рецептов. Клиент подтверждает конкретные материалы, плату банку и гонорар. Готовая вещь поступает сразу, с авторством изготовителя.
- **Сумка:** обычные применения и уникальные товары. Линза требует добровольного предъявления реликвии и отдельного согласия на осмотр; физический ответ записывает ведущий.
- **Таверна:** доска резервирует материальную награду; добровольная обычная способность может быть обещана исполнителю отдельной отметкой. После принятия отмену подтверждают оба либо ведущий. Выполнение и нестандартные услуги проверяет ведущий. Слухи помечаются непроверенными. Кости физические: ведущий вводит два результата d6, приложение распределяет банк.
- **Ритуал:** любые три целые части и два Фокуса, порошок, формула, скрытые выборы, раскрытие/ответ талисманами, последний выбор. У ведущего есть текст для чтения и механика каждого шага с изображениями. После начала обычные сделки/изготовление/способности прекращаются; сюжетные заявки остаются доступны до закрытия.
- **Итоги:** жизнь, свобода и сила Сарна отдельно от личных достижений. Ведущий подтверждает публичное сопоставление A+B+C, осознанное предложение Серафины и отречение Вельды. Свободные чудеса и новые последствия оформляются инструментами «Сюжет».

Проверки новой редакции: `pnpm e2e:hidden17`, `pnpm test`, `pnpm typecheck`, `pnpm build`. `pnpm e2e` и симулятор 12/30 продолжают проверять legacy-режим; их отчёты не являются прогоном нового финала. Живой баланс вечеринки автоматическими тестами не проверяется.

## Исправление автоматической выдачи обряда

Сюжетный перенос больше не выдаёт всем героям знание соединения. Стартовые источники полного способа есть у Вельды и Астры; сведения из игровых сцен подтверждает ведущий.

Для журнала, перенесённого старой версией, предусмотрен `packages/server/src/repair-migration-cli.ts`. Сначала остановите игровой сервер. Из окружения сервера с теми же данными и переменными выполните `pnpm --filter @fair/server exec tsx src/repair-migration-cli.ts --expected-seq N` для просмотра. Для записи добавьте `--apply --server-stopped --backup /data/repair-backup.sqlite`, указав новый путь резервной копии. `N` — текущий последний номер события, проверяемый повторно перед записью.

Исправление добавляет событие, сохраняет исходный журнал и создаёт резервную копию с правами 0600. Оно удаляет только знание соединения без доступного личного источника. После переноса допускаются только пауза/возобновление и обмены с неизменными знаниями; выдача знаний, показ документов и любые другие действия требуют отдельного разбора. Повторный запуск ничего не меняет. Перед записью проверяются инварианты и полное совпадение остальных данных партии. После операции запустите сервер и проверьте health.
