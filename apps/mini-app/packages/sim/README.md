# Симулятор вечера (`@fair/sim`)

Боты проходят весь вечер ярмарки против настоящего сервера через HTTP и WebSocket: подготовку, три акта по шесть кругов, закрытие и показ итогов. После прогона симулятор проверяет ответы сервера, инварианты, проекции игроков, журнал и покрытие, а затем пишет отчёт. Спецификация: `docs/superpowers/specs/2026-10-27-evening-design.md`.

## Запуск

Из `apps/mini-app`:

```sh
pnpm sim -- --players 12 --seed 1
pnpm sim -- --players 30 --seed 7 --keep
```

Без `--url` симулятор сам поднимает сервер. Он выбирает свободный порт и запускает `packages/server/src/index.ts` через бинарник `tsx` с окружением `DB_PATH=<out>/evening-<players>-<seed>.sqlite`, `ALLOW_DEV_AUTH=1`, `SESSION_SECRET=sim`, `BOT_POLLING=0` и `PORT=<порт>`. Явные значения перекрывают `apps/mini-app/.env`. От опроса настоящего бота дочерний сервер защищает только `BOT_POLLING=0`: пустой `BOT_TOKEN` в окружении не перекрывает значение из `.env`, сервер считает пустую переменную незаданной (`packages/server/src/config.ts`), так что `BOT_TOKEN` из `.env` сервер видит, но без опроса бот не запускается. Вывод сервера печатается, только если он не запустился. После прогона сервер получает `SIGTERM`, а если не завершился за 5 с, то `SIGKILL`.

Код выхода 0 означает, что все проверки прошли; 1 — что есть ошибка проверки или прогон прерван.

## Параметры

| Параметр | По умолчанию | Смысл |
| --- | --- | --- |
| `--players` | `12` | состав: `12` (ядро) или `30` (все роли) |
| `--seed` | `1` | зерно генератора: одно зерно даёт одну последовательность команд (с точностью до серверных id) |
| `--url` | нет | адрес уже работающего сервера; без него поднимается дочерний |
| `--out` | `./sim-out` | папка отчёта и базы (относительно `packages/sim`, если запуск через `pnpm sim`) |
| `--keep` | нет | не удалять базу `.sqlite` и папку `<out>/exports/` после прогона |

Дочерний сервер при закрытии ярмарки сам пишет выгрузку журнала в `<out>/exports/` (папка рядом с базой). Без `--keep` CLI удаляет её вместе с базой, с `--keep` она остаётся, и убрать её можно вместе с `sim-out`.

Папка `sim-out/` в `.gitignore`. Отчёты и базы не коммитятся.

## Что проверяется

- **responses**: каждый отказ из допустимых (`insufficient`, `reserved`, `limit`, `not_found`, `not_owner`, `phase`). `invalid` допустим только у `ability.use` из белого списка вида. Команды ведущего обязаны пройти, кроме позднего `lot.close` по торгу, который сервер уже закрыл по сроку. Нарочные пробы (`forbidden`) обязаны получить ожидаемый код. Просьбы со статусом `failed` должны иметь допустимые причины.
- **invariants**: `checkInvariants` на каждом снимке и `checkActStart` вокруг каждого `act.next`.
- **start**: после открытия у каждого 6 золота, ингредиенты по набору роли, стартовые реликвии и осколки.
- **views:act1 … views:revealed**: проекции игроков на том же `seq`, что и у ведущего. Золото и число вещей совпадают, чужих тайн и текста «Правды» в проекциях нет, после показа есть итоги и две цели. Набор ботов совпадает с присутствующими ролями.
- **closing**: после показа итоги в состоянии ведущего совпадают с `computeClosing` на том же состоянии. В конце акта III, после круга ответов, сценарий собирает алтарь пробуждения: ведущий исправлением «вещь у игрока» (причина «проверка готовности алтаря») отдаёт трём участникам стороны `wake` недостающие разные осколки и Фокусы, они кладут их на алтарь и вносят по 2 золота. Если Фокусов в игре не хватает, ведущий выдаёт Пепел, Пыль и золото на работу, и участник изготавливает Фокус сам. Затем ведущий отдаёт все три улики одному присутствующему (причина «проверка «Правды»»). Поэтому исход обязан быть `wake`, а «Правда» у этого игрока. Если при составе шаг невозможен (на стороне меньше трёх участников, осколок или улика в непроданном лоте), он пропускается со строкой «сценарий: …» в пропущенном.
- **coverage**: каждый тип команды хотя бы раз получил `ok`. Исключения: `offer.expire`, `consent.expire`, `session.reset`, а при 30 игроках ещё `lot.buyout`. Способность каждой присутствующей роли сработала хотя бы раз; враждебная, отражённая защитой, тоже засчитывается. Каждый вид вещи (`potion`, `ward`, `shape`) применён.
- **probes**: все нарочные пробы сделаны.
- **replay**: состояние, восстановленное из базы, совпадает с последней проекцией ведущего.
- **gold**: золото сходится с журналом событий (`checkGold`).

Пороги времени и размера только предупреждают: p95 не больше 300 мс, проекция игрока не больше 256 КБ. У проекции ведущего порога нет.

## Отчёт

Файл `<out>/evening-<players>-<seed>.md` на русском, семь разделов:

1. Параметры.
2. Ход вечера по актам.
3. Итоги: алтари, исход, «Правда».
4. Игроки.
5. Проверки.
6. Время и размер.
7. Вопросы владельцу.

В stdout печатается выжимка: результат, длительность, p95, размеры проекций, непокрытое, предупреждения по порогам, пропущенные проверки и вопросы владельцу. В отчёте предупреждения стоят в разделе 6, пропущенные проверки помечены в разделе 5, а в разделе 7 только вопросы к правилам.

## Режим `--url`

`--url` нужен только для локального сервера, запущенного отдельно (например, чтобы смотреть его лог). Требования:

- сервер запущен с `ALLOW_DEV_AUTH=1`: боты входят через dev-вход, а коды берут из `GET /api/dev/codes`;
- сессия свежая: фаза `setup`, ведущий не привязан или привязан к `userId = 100`.

Иначе прогон прерывается с понятной ошибкой. Симулятор никогда не посылает `session.reset`. После прогона сессия остаётся в фазе `revealed`, и для следующего прогона её нужно сбросить вручную. Воспроизведение журнала и проверка золота в этом режиме пропускаются, отчёт показывает это.

Против развёрнутого сервера (`https://wta5.ru/fair`) `--url` не годится. Настоящая игра должна идти без dev-входа: с ним войти за любого гостя смог бы кто угодно. К тому же прогон оставил бы сессию в `revealed` и привязал бы ведущего к `userId = 100`.

## Тесты

`pnpm --filter @fair/sim test`. Тест вечера на 12 игроков (зерно 1) поднимает сервер в процессе (`src/__tests__/server-fixture.ts`) и проверяет, что все проверки зелёные. Тест отчёта проверяет семь разделов и строку игрока.
