# Telegram Mini App «Ярмарка украденной магии». Спецификация 0.1

Дата: 23 октября 2026. Статус: проект на согласование. Правила игры берутся из `magic-fair-v0.2.md` и `game-data-v0.2.json`; этот документ описывает только приложение.

## 1. Зачем и что это

Приложение заменяет ведущего в двух ролях, которые его вымотали в прошлый раз: справочная «что это за вещь и что с ней делать» и судья финала. Оно хранит состояние одной игровой сессии на 12–30 телефонов, проверяет каждое действие по правилам, показывает каждому его роль и цели, считает достижения при закрытии и даёт ведущему пульт на восемь обязательных действий за вечер.

Это Telegram Mini App: веб-приложение, которое открывается внутри Telegram по кнопке бота. Отдельной установки нет, вход через Telegram-аккаунт гостя.

## 2. Границы первой версии

В первую версию входит:

- одна активная сессия на сервере, 12–30 игроков и один ведущий;
- загрузка содержимого игры из `game-data-v0.2.json`: роли, стороны, реликвии, осколки, улики, события, рецепты, тексты;
- раздача ролей по приглашениям, явка, пересчёт состава;
- экраны игрока: Роль, Сумка, Сделки, Мастерская, Алтари, События;
- экраны ведущего: Состав, Пульт, Журнал, Закрытие;
- сделки с резервом и подтверждением, мастерская, все способности 30 ролей, защита и враждебные действия, алтари, лоты с закрытыми ставками, события актов, скрытый осколок V, улики;
- закрытие ярмарки, проверка алтарей, исход, «Правда», подсчёт целей, показ результатов;
- журнал всех действий и исправления ведущего с причиной;
- обновления в реальном времени на всех телефонах.

Не входит в первую версию:

- мини-игры «Рунный контур» и «Дуэль блефа» как интерактив. В первой версии они играются вживую: ставку дуэли проигравший передаёт сделкой, а награду за рунный контур ведущий выдаёт исправлением «+1 золото» с причиной. Купонов на скидку в первой версии нет. «Торг за лот» входит, потому что это часть основного цикла;
- несколько одновременных сессий, история прошлых игр, статистика;
- выгрузка состояния в печатный вид (решение владельца: бумага включается до начала);
- уведомления через сообщения бота, кроме ссылки на вход;
- локализация, кроме русского.

## 3. Пользователи и доступ

Игрок. Открывает Mini App по ссылке-приглашению от ведущего. Видит только свою роль, свой инвентарь, общие вещи (алтари, лоты, события) и публичные имена остальных. Чужие цели, тайны, стороны и инвентари закрыты, кроме случаев, когда их открывает способность.

Ведущий. Один аккаунт. При запуске сервер печатает в лог одноразовый код ведущего; первое открытие Mini App с этим кодом в `startapp` привязывает аккаунт как ведущего и создаёт сессию. Telegram id ведущего в конфигурации не хранится. Ведущий видит всё, включая тайны и цели, и не играет.

Гость без роли. Открыл приложение без приглашения или после раздачи всех ролей: видит легенду и сообщение «обратитесь к ведущему».

Приглашения. При создании сессии сервер генерирует по одному коду на роль из символов `A–Z a–z 0–9 _ -`, не длиннее 64. Ведущий отправляет каждому гостю ссылку `t.me/<бот>?startapp=<код>` сам, любым способом. Такая ссылка работает только если у бота в BotFather настроен Main Mini App; кнопка из `/start` код не передаёт и служит для повторного входа уже привязанного аккаунта. Первое открытие по коду привязывает Telegram-аккаунт к роли; повторные открытия пускают только этот аккаунт. Ведущий может отвязать и перевыдать код. Списки гостей и соответствие «гость → роль» живут только на сервере сессии и не попадают в репозиторий.

## 4. Архитектура

Три части: клиент в Telegram, сервер с правилами, бот.

Клиент. Одностраничное приложение, открывается в WebView Telegram. При старте отправляет `initData` Telegram на сервер, получает свой снимок состояния и дальше держит WebSocket, по которому приходят события. Любое действие это команда на сервер; клиент ничего не считает сам, только показывает и валидирует форму до отправки, чтобы не слать заведомо невозможное.

Сервер. Один процесс. Всё состояние сессии в памяти, каждое изменение это событие, которое дописывается в журнал на диске до того, как рассылается клиентам. При перезапуске состояние восстанавливается проигрыванием журнала. Это даёт три вещи сразу: атомарность (один процесс, одна очередь команд), журнал для ведущего и восстановление после падения.

Бот. Нужен только для входа: отдаёт кнопку Mini App и принимает `startapp`. Логики в боте нет.

Поток команды: клиент отправляет `{id, type, payload}`. Сервер проверяет подпись `initData`, находит игрока, ставит команду в очередь, применяет к состоянию по правилам, если правила не нарушены, записывает событие в журнал, рассылает всем, кому оно видно, и отвечает клиенту результатом. Повторная команда с тем же `id` возвращает прежний результат и не применяется второй раз.

### 4.1. Стек

Это моё решение, владелец стек не выбирал. Критерии: один разработчик, одна сессия, 30 телефонов, два часа, Telegram.

- Сервер: Node.js 22, TypeScript, Fastify для HTTP, `ws` для WebSocket. Журнал событий в SQLite через `better-sqlite3`, одна таблица событий и таблица снимков. Правила как чистая функция `apply(state, command) → events | error` без обращения к базе, чтобы её можно было тестировать на массивах команд.
- Клиент: Vite, TypeScript, Preact или Vue 3 по вкусу разработчика. Для `initData`, `expand()`, кнопки «назад» и подтверждения закрытия используется официальный скрипт `telegram-web-app.js`; обёртка `@telegram-apps/sdk` от сообщества допустима поверх него. В каркасе сразу вызывается `expand()`, потому что Mini App открывается в компактном окне, а макеты рассчитаны на полный экран. Стили свои, без тяжёлых библиотек: RPG-стиль из макетов.
- Общий пакет типов между клиентом и сервером в монорепозитории: `apps/mini-app/{server,client,shared}`.
- Размещение: один маленький VPS, Docker Compose с сервером и Caddy для HTTPS (Telegram требует HTTPS). Для прогонов дома допустим туннель вроде Cloudflare Tunnel с локальной машины.
- Секреты: токен бота и секрет сессии в `.env`, в репозитории только `.env.example`.

Альтернатива, если захочется без своего сервера: Supabase или Firebase с правилами в edge-функциях. Отклонено, потому что атомарность сделок и очередь команд там даются труднее, чем в одном процессе.

## 5. Модель данных

Содержимое игры (неизменяемое за сессию) загружается из `game-data-v0.2.json`: `factions`, `roles`, `relics`, `shards`, `clues`, `recipes`, `events`, `story`, `resources`, `icons`.

Состояние сессии:

- `session`: `id`, `phase` (`setup` → `act1` → `act2` → `act3` → `closed` → `revealed`), `roster[]` (ключи ролей, выданных на эту игру), `nPresent` (число присутствующих на момент открытия, от него считается экономика), `clock` (старт акта, пауза, накопленное время), `altars[]`.
- `players[]`: `roleKey`, `telegramId`, `present` (пришёл), `gold`, `reservedGold`, `ingredients{ash,moon,dew}`, `items[]`, `abilityUsedInAct`, `pendingModifier` (отложенный эффект своей способности на следующее изготовление или покупку), `protection` (есть или нет и кто дал), `thorns`, `curse` (флаг, ничего не запрещает, не истекает, снимается только очищением; нужен для цели Эльмара), `discount` (от Лиры или Бубна, до конца акта), `side` (для свободных: выбранная сторона или пусто), `hostileAttemptsAgainstInAct`.
- `items[]` сквозной реестр: `id`, `kind` (`relic`, `shard`, `clue`, `potion`, `ward`, `focus`, `shape`), `ref` (имя реликвии, номер осколка, буква улики), `ownerPlayer` или `ownerAltar` или `lot`, `createdBy` (для изготовленных), `hiddenUntilAct` (для осколка V), `reservedForOffer`.
- `workshop`: остатки трёх ингредиентов.
- `offers[]`: `id`, `from`, `to`, `give[]`, `get[]`, `service` (для платы за способность), `status` (`pending`, `accepted`, `declined`, `cancelled`, `expired`), `expiresAt`.
- `lots[]`: `id`, `items[]`, `status` (`announced`, `openBidding`, `sealedBidding`, `sold`, `unsold`), `bids[]` (игрок, сумма, время), `fixedPrice`.
- `altars[]`: `side`, `contributions[]` (игрок, `itemId` или `gold`).
- `log[]`: все события с номером, временем игры и временем часов.
- `corrections[]`: часть журнала с полем `reason`.

Золото в резерве: деньги, которые лежат в незакрытой ставке или в неотвеченном предложении. Из `gold` они не вычитаются до результата, но `gold − reservedGold` это «доступно» для любых новых трат и для краж.

## 6. Правила на сервере: команды

Каждая команда проверяет фазу, принадлежность, лимиты и ресурсы, и либо применяется целиком, либо отклоняется с кодом ошибки, который клиент показывает словами. Ниже список по группам. Полные тексты правил в проекте игры; здесь только что проверяет сервер.

### 6.1. Сессия и состав (ведущий)

- `session.create(contentVersion)`: грузит содержимое, создаёт коды приглашений для всех 30 ролей.
- `session.setN(n)`: по таблице 6.1 проекта заполняет `roster` составом по умолчанию. Состав при 21–23 это роли 1–20 плюс резерв, при 24 и больше роли 1–20, торговый дом Т1–Т4 и резерв; это не префикс по `pos`, а правило из проекта.
- `session.toggleRole(roleKey)`: ведущий может заменить роль в составе на любую другую, если знает, кому что подойдёт. Сервер предупреждает, если торговый дом оказался не целиком или вошёл при составе меньше 24, но не запрещает. Коды приглашений выдаются только ролям из `roster`.
- `player.bind(code, telegramId)`: привязка аккаунта к роли. Первое открытие по коду.
- `player.setPresent(roleKey, bool)`: явка. Разрешено до `session.open`.
- `session.open()`: один раз. `nPresent` = число присутствующих. Пересчёт: стартовые наборы присутствующим, запас мастерской `ceil(nPresent/3)` каждого, вещи ролей вне состава и не пришедших в лоты первого акта по правилу 6.6 проекта: осколки I–IV всегда, осколок V только в третьем акте, улики B и C всегда, реликвии только с претендентом в составе, не больше четырёх лотов в первом акте, остальные переносятся во второй. Осколок V скрытно в инвентарь Лиры, улики B и C в инвентари Ады и Клёпы, если они пришли. Контакты: в первой версии текст контакта показывается как есть, а если роль, на которую он ссылается (`contacts[].role`), не в составе или не пришла, клиент добавляет пометку «не на ярмарке; вещь ищите на рынке». Подстановка по функции отложена до структурных контактов (раздел 15). Фаза `act1`, объявление «Ярмарка открыта», часы запущены.
- `act.next()`: из `act1` в `act2`, из `act2` в `act3`. Обнуляет применения способностей и счётчики враждебных попыток, снимает защиты, шипы, скидки и отложенные модификаторы, переносит неразыгранные лоты, пополняет мастерскую на `ceil(nPresent/6)`, публикует событие акта из содержимого. В `act2` создаёт лот «осколок IV + улика A». В `act3` открывает владельца V, если Лира в составе и пришла, иначе создаёт лот «осколок V». Проклятие при смене акта не снимается.
- `clock.pause()`, `clock.resume()`, `clock.extend(minutes)`: часы только информационные, фазы меняет ведущий.
- `session.close()`: из `act3` в `closed`. Отменяет все `pending` предложения и возвращает резервы, закрывает незавершённые лоты как `unsold`, замораживает всё, считает алтари, исход, «Правду» и цели (раздел 7). Требует подтверждения на клиенте.
- `session.reveal()`: из `closed` в `revealed`: игроки видят свои результаты и общий исход.
- `gm.announce(text)`: произвольное объявление всем.
- `gm.correct(playerKey, change, reason)`: с обязательной причиной меняет любое поле игрока: золото, ингредиент, владельца вещи, вклад на алтаре, защиту, шипы, проклятие, сторону свободного, возвращает применение способности или снимает отметку враждебной попытки, отменяет результат торга с возвратом ставки. Это единственный обход правил, и он весь в журнале как исправление. Приложение заменяет судью, поэтому ведущему нужен полный доступ, а не точечный.
- `gm.rebind(roleKey)`: отвязать аккаунт, выдать новый код.

### 6.2. Сделки

- `offer.create(to, give[], get[], service?)`: `give` и `get` это списки из золота, ингредиентов, вещей и слуха (слух это текстовая метка, ничего не переносит). В `get` вещи просят по названию (`wants`: вид и ref), потому что сумку адресата автор не видит; при принятии сервер сам находит у адресата свободную вещь с таким названием, а если её нет, предложение закрывается как `expired` с причиной `counterparty`. Клиент показывает адресату, чего у него нет, и не даёт принять. Сервер проверяет, что у автора есть всё из `give` и оно не в резерве, резервирует это, ставит срок ответа 5 минут. `service` помечает, что это плата за применение способности автора или адресата; это нужно целям Лиры и Бубна.
- `offer.accept(id)`: адресат. Сервер заново проверяет, что у адресата есть всё из `get` и не в резерве, и у автора всё ещё есть `give`. Переносит обоим одновременно, снимает резерв, записывает событие с обеими сторонами. Если проверка не прошла, предложение закрывается как `expired` с причиной.
- `offer.decline(id)`, `offer.cancel(id)`: адресат или автор. Резерв снимается.
- Истечение срока: сервер закрывает как `expired`.
- Вещи на алтаре и скрытый осколок V до третьего акта предлагать нельзя. Осколок V в третьем акте предлагать можно.
- Предложение, где обе стороны отдают только слух, принимать можно, но обменом для целей оно не считается: обмен засчитывается, когда хотя бы одна сторона передала золото, ингредиент или вещь. Так сказано в целях Миры и Орсона.

### 6.3. Мастерская

- `shop.buy(ingredient, count=1, abilityModifier?)`: цена 2 за штуку, запас уменьшается. Модификаторы от способностей меняют цену или источник (см. 6.5).
- `shop.craft(recipeId, abilityModifier?)`: проверяет ингредиенты по рецепту с учётом замены (Грета, Астра), золото с учётом скидок (Лира, Бубен, купон, Вельда для Фокуса) и шипов (+1), списывает всё, создаёт вещь с `createdBy`, снимает шипы и использованную скидку.

### 6.4. Алтари

- `altar.contribute(side, itemId | gold)`: осколок, Фокус или золото. Золото любое количество, учитывается по игрокам. Осколок V только с третьего акта. Нельзя класть вещь из резерва.
- `altar.withdraw(contributionId)`: только своё, до закрытия.

### 6.5. Способности

У каждой роли одна способность с `kind` из закрытого списка. Общие правила: одно применение за акт; применения с целью проверяют, что цель присутствует; враждебные проверяют, что по цели в этом акте ещё не было попытки, снимают защиту, если она есть, и в этом случае считаются заблокированными (попытка и применение расходуются, цель помечается). Применения, требующие согласия, создают запрос цели с кнопками «согласен / нет» и сроком 5 минут; эффект применяется после согласия. Отказ и истечение срока не расходуют применение: способность остаётся доступной в этом акте. На экране запроса написано «сначала договоритесь голосом, потом нажимайте», потому что телефон адресата может спать в кармане.

| kind | Роли | Что делает сервер |
| --- | --- | --- |
| `substituteIngredient` | Грета, Астра (копия) | Следующее изготовление автора принимает один любой базовый ингредиент вместо указанного в рецепте |
| `payAshWithGold` | Серафина | Следующее изготовление автора принимает 1 золото вместо одного Пепла из рецепта |
| `focusFree` | Вельда | Следующее изготовление Фокуса без платы 1 золота |
| `buyCheap` | Мира, Руна | Одна покупка ингредиента за 1 вместо 2 |
| `buyBulk` | Руф | Две покупки за 3 вместо 4 |
| `grow` | Брам, Астра (копия) | Списать 1 любой ингредиент, выдать 2 Росы из запаса; если Росы меньше 2, отказ |
| `swapIngredient` | Пим | 1 свой ингредиент на 1 любой другой из запаса, без платы |
| `buyFromBank` | Орсон | Одна покупка за 2 из банка, запас не нужен |
| `reforge` | Хельга | Своя изготовленная вещь (кроме Камня) на другую не дороже, плата 1 |
| `disassemble` | Грим | Своя изготовленная вещь исчезает, из запаса выдаются 2 ингредиента на выбор |
| `sellToBank` | Магда | Своя изготовленная вещь исчезает, автор получает 2 золота из банка |
| `discountOther` | Лира, Бубен, Астра (копия) | Следующее изготовление согласной цели дешевле на 1, до конца акта, не складывается |
| `protectSelf` | Туман | Автору защита до конца акта, если её нет |
| `protectOther` | Эльмар, Йорик | Цели защита до конца акта, если её нет |
| `transferProtection` | Клёпа | С согласия защищённого его защита переходит другому без защиты |
| `cleanseOther` | Ада, Кнут | С согласия цели снять проклятие или шипы. Очищение любым способом снимает и то и другое, как в 0.1 |
| `stealGold` | Никс, Долф | Враждебное. 1 доступного золота цели автору |
| `stealIngredient` | Сцилла | Враждебное. 1 указанный ингредиент цели автору |
| `thorns` | Ива | Враждебное. Цели шипы: следующее изготовление дороже на 1 |
| `inspectInventory` | Корвин | Автор получает снимок инвентаря цели (без целей и тайн) |
| `sniffIngredient` | Сив | Автор получает список присутствующих, у кого есть указанный ингредиент |
| `knowGold` | Торвин | Автор получает точное золото цели |
| `askSide` | Марта | Цель получает запрос и обязана ответить одной из сторон или «свободный»; ответ приходит автору. Сервер знает правду и помечает ложь в журнале для ведущего, игроку не показывает |
| `askYesNo` | Веста | Автор пишет вопрос, цель отвечает «да / нет», ответ приходит автору. Честность на игроке, сервер только записывает |
| `copyAbility` | Астра | Выбор одного из `grow`, `substituteIngredient`, `discountOther` с согласия владельца оригинала, если он в составе |

Всего 25 видов. Очищение зельем: `item.use(potionId, target?)` с согласия цели, если цель не автор; снимает проклятие или шипы. Камень облика: `item.use(shapeId)` на себя, с полем «новое имя или образ», которое становится публичной подписью. Талисман: `item.use(wardId)` даёт защиту себе, если её нет.

### 6.6. Лоты и торг

- Лот создаётся сервером (события актов, пересчёт) и публикуется всем.
- `lot.openBidding(id)` ведущий: две минуты открытого торга, это только таймер и объявление.
- `lot.sealedBids(id)` ведущий: окно закрытых ставок 90 секунд. `lot.bid(id, amount)`: ставка из доступного золота, резервируется, можно поднять до закрытия окна. По окончании сервер выбирает максимум, при равенстве жребий, переносит вещи победителю, списывает ставку в банк, снимает остальные резервы.
- Если ставок нет, лот переходит в `fixedPrice` 4: `lot.buyout(id)` первому, у кого есть 4 доступных.
- Ставки на лот не расходуют лимит мини-игр.

### 6.7. Свободные и сторона

- `player.chooseSide(side)`: только роли со стороной `free`, только до перехода в `act3`. Один раз. Хранится закрыто, учитывается при исходе.

### 6.8. Улики и «Правда»

Улики это вещи `kind=clue`. Ничего особенного на сервере, кроме проверки при закрытии: игрок с тремя уликами получает достижение «Правда», и ведущему показывается текст `story.truth`.

## 7. Закрытие: что считает сервер

1. Алтари. Для каждого: осколков с разными номерами ≥ 3, Фокусов ≥ 2, золота ≥ 6, разных игроков в золоте ≥ 3. Готовых не больше одного по построению; если по ошибке данных два, сервер выбирает ни одного и пишет в журнал предупреждение ведущему.
2. Исход: сторона готового алтаря или «сердце спит».
3. Достижение «исход»: игроки стороны исхода и свободные, выбравшие её.
4. «Правда»: игрок с тремя уликами. Улики ролей вне состава ушли в лоты первого акта, поэтому все три всегда в игре.
5. Личные цели. Каждая цель в содержимом описана одним условием из закрытого списка (проект, раздел 12). Сервер вычисляет их по инвентарю на момент закрытия и по журналу: продажи своих вещей по `createdBy` и `offer.accepted` с золотом, обмены с разными игроками по `offer.accepted`, плата за услугу по `offer.service`, применения способностей по событиям, вклады по `altar.contribute` без последующего `withdraw`, переданные вещи по `offer.accepted`.

Условия в содержимом задаются структурно, например `{"type":"holdItem","ref":"Корона пепла"}`, `{"type":"goldAtLeast","value":12}`, `{"type":"soldCrafted","count":2,"distinctBuyers":2,"minPrice":1}`. Перевод 60 текстовых целей в такие условия это часть работы над содержимым; пока цели в данных текстовые.

## 8. Экраны

Макеты и подписи на странице `../prototypes/magic-fair-v2.html`, раздел «Макеты приложения». Здесь только что на экране и какие команды он вызывает.

Игрок:

- Роль: портрет, имя, титул, сторона, легенда, предыстория, цели с состоянием, способность с кнопкой и остатком, контакты с именами, тайна, слух, кнопка выбора стороны у свободных. Команды: `ability.use`, `player.chooseSide`.
- Сумка: золото доступное и в резерве, ингредиенты, вещи с подписью откуда, кнопки «предложить», «на алтарь», «использовать». Команды: `offer.create` (переход), `altar.contribute`, `item.use`.
- Сделки: входящие с кнопками, исходящие с отменой, форма нового предложения, история. Команды: `offer.*`.
- Мастерская: запас, покупка, рецепты с проверкой, активные скидки и шипы. Команды: `shop.*`.
- Алтари: три или четыре алтаря с вкладами по игрокам, «вложить» и «забрать своё», состояние осколка V. Команды: `altar.*`.
- События: лента событий, открытый лот со ставкой, запросы на согласие (очищение, перенос защиты, вопросы Марты и Весты), мини-игры как справка. Команды: `lot.bid`, `lot.buyout`, ответы на запросы.

Ведущий:

- Состав: `n`, список ролей по порядку с привязкой и явкой, коды приглашений с кнопкой «скопировать ссылку», пересчёт и «открыть ярмарку». Команды: `session.setN`, `player.setPresent`, `gm.rebind`, `session.open`.
- Пульт: часы, пауза, продление, следующий акт с описанием последствий, управление лотом, объявление, «закрыть ярмарку» с подтверждением. Команды: `clock.*`, `act.next`, `lot.openBidding`, `lot.sealedBids`, `gm.announce`, `session.close`.
- Журнал: все события с фильтром по игроку и типу, пометки лжи в `askSide`, форма исправления. Команды: `gm.correct`.
- Закрытие: результат по алтарям, исход и его текст, «Правда» и её текст, список достижений, сводка целей, «показать результаты». Команда: `session.reveal`.

Общие элементы: верхняя полоса с актом и временем, нижняя панель вкладок с иконками, модальные подтверждения на необратимые действия (ставка, вклад, применение враждебной способности, закрытие).

## 9. Telegram

- Бот создаётся через BotFather, у него настроен Mini App с адресом клиента. Команда `/start` отвечает кнопкой «Открыть ярмарку».
- Клиент читает `initData` через SDK и отправляет серверу в первом запросе. Сервер проверяет подпись по токену бота и срок (не старше 24 часов), извлекает `user.id` и `start_param` с кодом приглашения.
- Сессия клиента после проверки: короткоживущий токен в памяти клиента, передаётся в WebSocket при подключении. Перезапуск приложения внутри Telegram повторяет вход по `initData`.
- Тема: приложение использует свои цвета, а не тему Telegram, потому что стиль RPG важнее; кнопка «назад» и подтверждение закрытия через SDK.
- Уведомлений через бота в первой версии нет: все 30 человек в одной квартире, объявления идут в приложении и голосом.

## 10. Реальное время и надёжность

- WebSocket с сервером, при обрыве клиент переподключается с экспоненциальной паузой и запрашивает снимок состояния с номером последнего виденного события; сервер досылает пропущенное.
- Каждая команда несёт `id`, сгенерированный клиентом. Сервер хранит результаты по `id` до конца сессии. Двойное нажатие и повтор после обрыва безопасны.
- Все таймеры (срок предложения, окно ставок, срок согласия) считает сервер и присылает моменты истечения; клиент только рисует обратный отсчёт.
- Часы акта информационные. Переходы фаз делает только ведущий кнопкой. Пауза останавливает отсчёт и продлевает все сроки на длительность паузы.
- Падение сервера: при старте проигрывается журнал, клиенты переподключаются сами. Ведущий видит в пульте «сервер перезапущен в 14:32», чтобы проверить, не потерялось ли последнее действие.
- Сервер и клиент в одном часовом поясе не нуждаются: везде время от начала сессии.

## 11. Данные, конфигурация, секреты

- Содержимое игры: `docs/design/game-data-v0.2.json` копируется в пакет сервера при сборке; версия содержимого пишется в сессию.
- Конфигурация сервера: `.env` с токеном бота, секретом для токенов клиентов, адресом клиента, путём к базе. В репозитории `apps/mini-app/.env.example` с пустыми значениями.
- База сессии: один файл SQLite на сессию в каталоге данных, вне репозитория.
- Персональные данные: Telegram id и имя хранятся только в базе сессии. Экспорт журнала для разбора после игры заменяет id на ключ роли.

- Первая загрузка клиента до 1 МБ, портреты подгружаются лениво.

## 13. Тестирование

- Правила: чистая функция `apply` тестируется на сценариях из команд без сервера. Обязательные сценарии: каждый из 25 видов способностей в успешном и отклонённом случае; сделка с резервом и обоими исходами; истечение; враждебная попытка в защиту; два ритуала по ошибке; закрытие с подсчётом всех 60 целей на подготовленном состоянии; пересчёт состава для `n` в 12, 17, 23, 24, 30 против таблиц проекта.
- Полный вечер: скрипт на 17 ботов-клиентов проигрывает заготовленный сценарий от `session.create` до `session.reveal`, проверяет журнал и результаты.
- Нагрузка: 30 клиентов шлют команды с частотой «каждый раз в 10 секунд» два часа; память и задержки в пределах.
- Устройства: ручной прогон на трёх телефонах перед домашним тестом на 12 человек.

## 17. Решения, принятые при проверке спецификации

Разработчик-рецензент задал девять вопросов. Ответы ниже приняты мной по правилам проекта; владелец может их пересмотреть.

- Состав это набор ролей, а не число: `setN` даёт состав по умолчанию, ведущий может менять роли вручную.
- Контакты в первой версии показываются текстом, с пометкой, если роль не на ярмарке. Структурные контакты отложены вместе со структурными целями.
- Способность Серафины добавлена как 25-й вид. Очищение снимает и проклятие, и шипы.
- Купонов в первой версии нет; награду за живую мини-игру ведущий выдаёт исправлением.
- Осколок V без Лиры выходит лотом в третьем акте, не в первом.
- Улики отсутствующих уходят в лот первого акта, поэтому «Правда» достижима всегда.
- Проклятие это флаг без эффектов, не истекает, снимается только очищением.
- Исправления ведущего универсальные, с обязательной причиной.
- Экономика считается от присутствующих, состав от подтвердивших.
- Ведущий опознаётся одноразовым кодом из лога сервера, его Telegram id в конфигурации нет.
- Срок согласия 5 минут, отказ и истечение не сжигают применение.
- Обмен одними слухами не считается обменом для целей.
