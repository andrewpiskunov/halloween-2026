# Этап 6: прогон полного вечера, экспорт журнала, памятка ведущего

Статус: реализовано (ветка `evening`). Перед реализацией проверено строителем (38 уточнений внесены), по ходу внесены решения контролёра (разделы 2.1, 2.3, 3.6, 4, 5) и итоги прогонов (раздел 10). Решения владельца не запрашивались (он выбрал продолжать без вопросов). Спорные места решены по умолчанию и помечены «решение здесь»; список в разделе 9.

Источники: спецификация Mini App (`docs/design/mini-app-spec.md`, разделы 2, 10, 13, 14 пункт 6, 16), спецификации этапов 3 и 5 (`docs/superpowers/specs/2026-10-27-abilities-design.md`, `2026-10-27-closing-design.md`), код движка и сервера в `apps/mini-app`.

## 1. Зачем и границы

### 1.1. Зачем

План поставки (§14 п. 6) завершается прогоном полного вечера скриптом и живым тестом на 12 человек. До живого теста приложение целиком никто не проходил: тесты проверяют движок по частям, e2e ведёт двух игроков через десять шагов. Прогон вечера гоняет настоящий сервер через HTTP и WebSocket с 12 и с 30 игроками по всем трём актам до показа итогов и проверяет то, что видно только на целом вечере: совместимость подсистем, воспроизведение журнала, утечки в проекциях, время ответа и размер рассылки на 30 телефонов. Найденные дефекты чинятся в этом же этапе. Для живого теста нужны ещё две вещи: выгрузка журнала для разбора после игры (спецификация §16 обещает её, но в коде её нет) и памятка ведущему с бумажными запасными ходами.

### 1.2. Входит

- Пакет `@fair/sim` (`apps/mini-app/packages/sim`): прогон вечера против работающего сервера, боты игроков и ведущего, сценарий, проверки, отчёт, тест вечера в процессе.
- Вынос проверок инвариантов из тестовых помощников в модуль `@fair/shared`; вынос `COMMAND_TYPES` из `ws.ts` в `@fair/shared`.
- Исправления дефектов, которые найдёт прогон, каждое с модульным тестом.
- Выгрузка журнала: `GET /api/gm/export` для ведущего, автоматическая запись файла при закрытии ярмарки, кнопка «Скачать журнал» на пульте.
- Удаление `telegramId` из проекции игрока (`me.player`): клиент его не читает.
- Памятка ведущего для живого теста: `docs/design/gm-runbook.md`.
- Обновление `docs/design/mini-app-spec.md` (§13 тестирование, §16 экспорт) и `README.md` пакета.

### 1.3. Не входит

- Сам живой тест и правки по его итогам.
- Изменения правил игры. Если прогон покажет, что правило мешает (цель недостижима без определённого гостя), это идёт в отчёт как вопрос владельцу.
- Нагрузочное тестирование сверх 30 игроков, многочасовые прогоны, бенчмарки SQLite.
- Боты, играющие «умно». Боты выполняют покрытие, а не стратегию.
- Интерактив мини-игр, вторые сессии, статистика (вне первой версии по §2).

## 2. Симулятор вечера

### 2.1. Устройство

Пакет `@fair/sim`: зависимости `@fair/shared` (значения, не только типы: это не клиент) и `ws`; `tsx` и `vitest` для запуска и тестов; у пакета есть скрипты `sim`, `test`, `typecheck`, чтобы он входил в `pnpm -r`. В корневом `package.json` добавляется `"sim": "pnpm --filter @fair/sim sim"`. Библиотечный вход `runEvening(options): Promise<EveningResult>`, CLI `src/cli.ts`. Запуск `pnpm sim -- --players 30 --seed 7`. Одно зерно воспроизводит команды с точностью до результата жребия при равных ставках: настоящий сервер решает ничью случайно. Параметры:

| Параметр | По умолчанию | Смысл |
| --- | --- | --- |
| `--players` | `12` | состав: `12` (ядро) или `30` (все роли) |
| `--seed` | `1` | зерно генератора; одно зерно даёт одну последовательность команд (типы и параметры с точностью до серверных id) |
| `--url` | нет | адрес работающего сервера; без него скрипт сам поднимает сервер |
| `--out` | `./sim-out` | папка отчёта и базы |
| `--keep` | нет | не удалять базу и папку `<out>/exports` после прогона |

Без `--url` CLI находит свободный порт (`net.createServer().listen(0)`), запускает бинарник `tsx` напрямую (без обёртки `pnpm`, чтобы `SIGTERM` доходил) на `packages/server/src/index.ts` с окружением `DB_PATH=<out>/evening-<players>-<seed>.sqlite`, `ALLOW_DEV_AUTH=1`, `SESSION_SECRET=sim`, `BOT_POLLING=0`, `PORT=<порт>`, `CONTENT_PATH` по умолчанию; явные значения нужны, потому что сервер читает `apps/mini-app/.env`. От опроса настоящего бота дочерний сервер защищает только `BOT_POLLING=0`: пустой `BOT_TOKEN=` не перекрывает `.env`, потому что `config.ts` считает пустую переменную незаданной. Автозапись выгрузки оставляет `<out>/exports/`; без `--keep` CLI удаляет эту папку вместе с базой. Ждёт `GET /api/health`, после прогона посылает `SIGTERM` и ждёт выхода.

С `--url` прогон идёт против чужого сервера: перед стартом проверяется, что фаза `setup` и ведущий не привязан (или привязан именно `userId = 100`), иначе прогон завершается с понятной ошибкой; `session.reset` симулятор не посылает никогда. Воспроизведение журнала (раздел 3.4) в этом режиме пропускается, и отчёт это показывает.

Вход ботов через dev-вход `POST /api/auth` с `{ dev: { userId, startParam: код } }`. Коды берутся из `GET /api/dev/codes` после того, как ведущий задал состав. Ведущий входит с кодом ведущего и `userId = 100`, игроки с `userId = 1000 + номер в составе`. Успешный вход с возвращённой ролью засчитывается в покрытие как `player.bind` (по WebSocket эту команду не послать).

### 2.2. Боты

Один бот на игрока и один на ведущего. У каждого соединение WebSocket с последней проекцией, её `seq` и очередью результатов команд. Боты не действуют сами по себе: оркестратор вызывает их по очереди в порядке состава, поэтому при одном зерне последовательность команд воспроизводится. Ход игрока = ответы на все входящие (предложения, просьбы согласия) + одно действие из политики акта. «Купить» и «изготовить» это два хода.

Генератор: mulberry32 от зерна, один на прогон. `Math.random` в симуляторе не используется. Боты выбирают вещи и цели по стабильным ключам (роль, вид, `ref`), а не по порядку серверных id, иначе одно зерно даёт разные команды.

Команда ждёт результата; результат записывается в журнал прогона с номером хода, автором, командой и ответом.

### 2.3. Сценарий

Сценарий один для обоих составов; при 12 часть ролей отсутствует. Кругов в акте шесть (решение здесь).

**Подготовка.** Ведущий: `session.setN`; один раз `session.toggleRole` (снять и вернуть одну роль); все игроки входят по кодам; `player.setPresent` для каждого; репетиция «телефон сел»: `gm.rebind` для одного игрока и повторный вход под новым `userId` по новому коду; `session.open`. Проверка: ярмарка открыта, у каждого игрока стартовые золото и вещи по содержимому.

**Акт I (6 кругов).** Политика игрока по порядку:
1. Применить свою способность, если в этом акте ещё не применял и её можно собрать (раздел 2.4); враждебные (`stealGold`, `stealIngredient`, `thorns`) в акте I пропускаются.
2. Купить ингредиент и на следующем ходу изготовить рецепт, если хватает золота (роли с целями про изготовление делают то, что нужно их целям по `goals.ts`; остальные случайный рецепт).
3. Предложить сделку соседу по составу (следующий присутствующий): моя вещь за золото, моя вещь за просьбу по названию (`wants`), золото за `wants`, с вероятностью 1/3 каждая; раз за акт одна услуга (`service`). Чужих вещей игрок не видит, поэтому сделок «золото за конкретную чужую вещь» нет.
4. Положить на алтарь своей стороны осколок, фокус или 2 золота; свободная роль выбирает сторону (`player.chooseSide`) на первом ходу второго круга.
5. Раз за акт у одного бота: `offer.cancel` своего висящего предложения; у другого: `altar.withdraw` своего вклада с последующим повторным вкладом.

Роли, чья способность требует изделия (Грим, Хельга, Магда), с круга 3 получают покупку и изготовление раньше политики, если изделия нет.

Ответы на входящие: принять предложение, если после него золото не ниже 1, иначе отклонить; просьбу согласия о способности принять всегда, о вещи с вероятностью 3/4 (иначе покрытие падает случайно на части зёрен).

Нарочная проба акта I: один игрок шлёт чужой `consent.accept`, ожидается `forbidden`.

**Акт II.** Лоты создаёт сам `act.next` (в акте II лот «Осколок IV + улика A», при 12 ещё остаётся лот акта I). Одновременно торг идёт только по одному лоту, открытый торг сам не заканчивается, закрывает его только перевод в закрытые ставки. Ход ведущего по кругам: круг 1 `lot.openBidding` по лоту акта II; круг 2 `lot.sealedBids` по нему; круги 2–3 игроки ставят (ставка выше своей прежней, видимой в `lots[].bids`, в пределах золота; иначе не ставят); круг 4 `lot.close` от ведущего (если сервер уже закрыл торг по сроку, отказ `invalid` ведущему допустим, когда лот уже не в `sealedBidding`). При 12 затем второй лот: `sealedBids` без ставок → `close` → `fixedPrice` → один бот `lot.buyout`. При 30 второго лота нет, `lot.buyout` из обязательного покрытия исключён. Ведущий делает одно исправление «+1 золото» с причиной «награда за рунный контур» и один раз `clock.extend`. Один бот делает `consent.cancel` своей просьбы. Враждебные способности разрешены. Нарочная проба: игрок шлёт `lot.close`, ожидается `forbidden`.

**Акт III (6 кругов).** Как акт I без запрета на враждебные, плюс вещи: зелья, талисманы, обличья применяются на себя и на других. Ведущий посылает одно объявление. Детерминированный шаг: первый отказ на просьбу о вещи, если отказов ещё не было (иначе покрытие `consent.decline` зависит от случая). На последнем круге ведущий ставит часы на паузу и снимает (`clock.pause`, `clock.resume`); в промежутке ботов не вызывают. Нарочная проба: игрок шлёт `session.close`, ожидается `forbidden`. После последнего круга и круга ответов два детерминированных шага. Сбор алтаря (`assembleAltarOnce`): ведущий исправлением `itemOwner` с причиной «проверка готовности алтаря» отдаёт трём присутствующим участникам стороны `wake` недостающие разные осколки и Фокусы (при нехватке Фокусов выдаёт Пепел, Пыль и золото, и участник изготавливает Фокус), участники кладут их на алтарь и вносят по 2 золота; алтарь доходит до порога готовности (3 осколка, 2 Фокуса, 6 золота от трёх вкладчиков). «Правда» (`tellTruthOnce`): ведущий отдаёт улики A, B, C одному присутствующему. Без этих шагов случайная игра ботов заканчивалась исходом «Сердце спит» и «Правдой» без держателя, и ветки итогов с готовым алтарём не проверялись. Невозможный при составе шаг пропускается с пометкой в пропущенном. При показе итогов проверка `closing` требует исход `wake`, держателя «Правды» и совпадения итогов с `computeClosing`.

Перед каждым `act.next` оркестратор делает круг только из ответов на входящие, чтобы просьбы не закрывались сменой акта.

**Закрытие.** Ведущий: `session.close`. Проверки раздела 3. Исправление после закрытия: цель с индексом 0 первого присутствующего отмечается `true`, затем снимается (`null`). `session.reveal`. Объявление после показа итогов.

**Разбор.** Отчёт, воспроизведение журнала (3.4), остановка сервера.

### 2.4. Способности

Модуль `src/uses.ts`: `useFor(kind, view, rng): AbilityUse | null`. `null` означает, что предпосылок нет (нет вещи для перековки, нет цели для защиты), и бот идёт к следующему пункту политики. Таблица покрывает все 25 видов; `copyAbility` копирует `grow`. Цели выбираются среди присутствующих, не себя. Для способностей с согласием `ok` на `ability.use` означает только «просьба создана»; «способность сработала» считается по записи в `actions` или по `ConsentClosed accepted`. Просьба видна одобряющему в `view.requests` с `id` и статусом `pending`, срок 5 минут.

Отказы `invalid`, которые зависят от скрытого состояния другого игрока («у цели уже есть скидка», «у защищённого нет защиты», «условия изменились» после согласия), перечислены белым списком пар «вид + текст отказа» в `uses.ts` и допустимы. Любой другой `invalid` или `internal` на применение своей способности роняет прогон. В прогоне на 30 каждая роль обязана хотя бы раз получить срабатывание своей способности.

## 3. Проверки

Прогон падает с ненулевым кодом, если хоть одна проверка не прошла. Результаты печатаются в отчёт.

### 3.1. Ответы на команды

Каждый `ok: false` сравнивается с допустимыми отказами шага: `insufficient`, `reserved`, `limit`, `not_found` (вещь ушла между ходами, в том числе «нужной вещи нет» при `wants`), `not_owner`, `phase` (после смены акта или на паузе), белый список `invalid` из 2.4. Недопустимые везде: `internal`, прочие `invalid`, `forbidden` вне нарочных проб.

### 3.2. Инварианты

`checkInvariants`, `checkGold`, `checkActStart` переезжают из `packages/shared/src/__tests__/helpers.ts` в `packages/shared/src/invariants.ts` (без чтения файлов и без `node:*`: пакет собирается и в клиент) и экспортируются из пакета; тесты импортируют их через прежний помощник. Прогон вызывает `checkInvariants` на состоянии ведущего после подготовки, после каждого акта, после закрытия и после показа; `checkActStart` на снимках до и после каждого `act.next`; `checkGold` по событиям журнала из базы в конце (в тесте через `store.all()`, в CLI после остановки сервера; при `--url` пропускается).

### 3.3. Проекции игроков

Проекции приходят асинхронно, поэтому сверка идёт только при равных `seq`: оркестратор ждёт, пока у всех соединений `seq` равен `seq` последнего результата. После каждого акта и в конце для каждого бота:
- золото и число вещей в проекции равны состоянию ведущего;
- в проекции нет ключа `telegramId` (проверка по структуре, не по подстроке: число совпало бы с метками времени), нет чужих объектов `Player`;
- `src/privacy.ts`: в строковом виде проекции нет чужих `goals`, `secret`, `backstory`, `motivation`, строк `acting`, кодов приглашений и кода ведущего; исключаются строки, которые есть в своей роли или в общих данных (`contacts`, `public`, `clues`), так как тексты целей у ролей повторяются;
- в `revealed` проекция содержит `closing` и две цели. Текста «Правды» в проекции игрока нет ни в одной фазе (это и сейчас так).

`actions` и `offers` не проверяются: чужое золото и вещи приходят туда законно (`knowGold`, `inspectInventory`).

### 3.4. Воспроизведение журнала

`runEvening` принимает необязательный `replay: () => Promise<GameState>`. CLI передаёт функцию, которая после остановки сервера открывает ту же базу через `Game.open(new EventStore(path), content, opts)` (глубокий импорт из `@fair/server/src/...`; у пакета сервера нет `exports`, и зависимость от него есть только у CLI). Сравнение: `JSON.parse(JSON.stringify(state))` с последней проекцией ведущего (у которой `seq` равен последнему результату) через глубокое равенство. Расхождение роняет прогон.

### 3.5. Время и размер

Для каждой команды измеряется время от отправки до результата. В отчёт: p50, p95, максимум; размер самой большой проекции игрока и ведущего в байтах исходного JSON; общее время. Пороги (решение здесь): p95 ≤ 300 мс, проекция игрока ≤ 256 КБ; превышение печатается предупреждением, не роняет прогон. Проекция ведущего несёт всё содержимое и состояние, её размер печатается без порога и упоминается в отчёте как материал для отложенного пункта «содержимое в каждом событии».

### 3.6. Покрытие

`COMMAND_TYPES` переезжает из `ws.ts` в `@fair/shared/commands.ts`. В конце прогона проверяется: каждый тип команды встретился хотя бы раз с `ok`, кроме `offer.expire`, `consent.expire`, системного `lot.close`, `session.reset`; при 30 также кроме `lot.buyout`. Каждый вид способности присутствующих ролей сработал хотя бы раз (у враждебных видов заблокированная попытка считается как «сработала (отражена защитой)»); каждый вид вещи (`potion`, `ward`, `shape`) применён хотя бы раз. Недостающее печатается, прогон падает.

## 4. Отчёт

Файл `<out>/evening-<players>-<seed>.md` на русском и выжимка в stdout. Разделы:
1. Параметры: состав, зерно, адрес сервера, длительность.
2. Ход вечера по актам: сделки (принято, отклонено, отменено), изготовления, применения способностей и вещей, вклады и изъятия, лоты с победителями, объявления, исправления. Столбца «истекло» нет: в минутном прогоне сроки не истекают.
3. Итоги: алтари, исход, держатель «Правды», предупреждения.
4. Игроки: роль, золото в начале и в конце, вещи, способность (сработала или причина), цели из 2, исход, Правда.
5. Проверки раздела 3 с результатом.
6. Время и размер.
7. Вопросы владельцу: правила, которые прогон не смог выполнить, с указанием роли.

В разделе 7 только вопросы к правилам. Превышения порогов времени и размера печатаются предупреждениями в разделе 6, пропущенные проверки (например, воспроизведение при `--url`) помечаются в разделе 5.

## 5. Выгрузка журнала

`GET /api/gm/export`, токен в заголовке `Authorization: Bearer <токен>` или в `?token=` (для кнопки; только на этом маршруте). Нет токена или он неверен → 401; токен не ведущего или токен «за игрока» (`as`) → 403, как в `/api/gm/as`. Ответ JSON с `Content-Disposition: attachment; filename="evening-<дата>.json"`, дата по часовому поясу `Europe/Moscow`; заголовки `Cache-Control: no-store` и `Referrer-Policy: no-referrer`, чтобы адрес с токеном не оседал в кэше и не уходил дальше:

```
{ "exportedAt": число, "contentVersion": "0.2", "events": [...], "state": {...} }
```

Чистая функция `stripPersonal(events, state)` в `packages/server/src/export.ts` убирает: в событиях `PlayerBound.telegramId`, `FairOpened.players[*].telegramId`, `SessionReset.gmTelegramId`, коды в `SessionCreated.codes`, `SessionReset.codes`, `InviteRebound.code`; в состоянии `gmTelegramId`, `bindings`, `players[*].telegramId`, `invites`, `gmCode` (`roster` это массив ключей ролей, личных данных в нём нет). Тест: большие вымышленные id, поиск по ключам и значениям в строковом виде. Выгрузка не предназначена для воспроизведения (привязки удалены).

Автозапись: в `index.ts` подписка `game.subscribe` ловит переход в `closed` с новым `closedAt` и пишет выгрузку в `<папка базы>/exports/evening-<closedAt>.json`; тот же файл перезаписывается на `Revealed` и на каждом `Corrected` после закрытия (исправления меняют итоги). При `DB_PATH=:memory:` файл не пишется. Ошибка записи логируется и не мешает игре.

На пульте в блоке «Сброс игры» кнопка «Скачать журнал»: открывает `location.origin + BASE + 'api/gm/export?token=<ownToken>'` через `Telegram.WebApp.openLink`, а без Telegram через `window.open`. Подпись: «Файл также сохраняется на сервере при закрытии ярмарки».

## 6. Памятка ведущего

- За день: сервер и бот, сброс игры, проверка входа с двух телефонов, печать бумажной страховки (роли с кодами, пороги алтарей, рецепты, таблица исходов).

## 9. Решения здесь

1. Шесть кругов в акте.
2. Симулятор гоняет настоящий сервер через HTTP и WebSocket, а не движок напрямую.
3. Воспроизведение журнала передаётся в `runEvening` снаружи; зависимость от сервера есть только у CLI (глубокий импорт), тест вечера живёт в пакете симулятора.
4. Пороги времени и размера предупреждают, а не роняют прогон; у проекции ведущего порога нет.
5. Выгрузка без `telegramId`, привязок, кода ведущего и кодов приглашений.
6. Автозапись выгрузки при закрытии с перезаписью на показ и исправления.
7. Кнопка выгрузки открывает адрес с токеном в `query`; сервер принимает токен в `query` только на этом маршруте.
8. Враждебные способности в акте I пропускаются, вещи применяются в акте III.
9. Правила игры не меняются; вопросы идут в раздел 7 отчёта.
10. `telegramId` убирается из проекции игрока.
11. Просьбы о способностях боты принимают всегда, о вещах с вероятностью 3/4.
12. При 30 `lot.buyout` не входит в обязательное покрытие: лот там один, и ставка его продаёт.

## 10. Итоги прогонов

Пять обязательных прогонов и два дополнительных (12 игроков с зерном 20 и 30 игроков с зерном 20) прошли все проверки раздела 3. В правилах движка прогоны дефектов не нашли; два дефекта обвязки описаны ниже.

Два дефекта нашлись по ходу реализации, оба исправлены:
- Разбор команд WebSocket не пропускал `null` во вложенных полях. Ведущий не мог с пульта снять отметку цели, облик или выбор стороны. Исправлено вместе с тестом.
- После переподключения того же аккаунта бот симулятора начинал нумерацию команд заново, и защита сервера от повторов возвращала результат старой команды с тем же `id`. Исправлено в клиенте бота: префикс `id` теперь уникален для каждого подключения. Игроков это не касалось: настоящий клиент (`packages/client/src/api.ts`, `send`) берёт `id` каждой команды из `crypto.randomUUID()`, а после обрыва повторяет неотвеченные команды с тем же `id`, на что защита от повторов и рассчитана.

Вопросов владельцу прогоны не дали.

Памятка ведущего для живого теста: [`docs/design/gm-runbook.md`](../../design/gm-runbook.md).
